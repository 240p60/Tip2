## 1. Сравнение сервисов для доставки тестовых сборок iOS

Три наиболее популярных сервиса для доставки iOS-сборок тестировщикам:

| Критерий | **TestFlight (Apple)** | **Firebase App Distribution** | **Diawi** |
|----------|------------------------|------------------------------|-----------|
| **Владелец** | Apple | Google | Diawi.com (независимый) |
| **Стоимость** | Бесплатно, но требует Apple Developer Program — **$99/год** | Бесплатно (в рамках Firebase free tier), собственный сертификат Apple обязателен | Бесплатный тариф с ограничениями, Pro — от **$13/мес** |
| **Простота настройки для разработчика** | Средняя: нужен Apple ID, membership, provisioning profile, загрузка через Xcode → App Store Connect; сборка проходит модерацию Apple (может занять 24-48 ч на первую) | Простая: загрузка `.ipa`, приглашение тестеров по email; но всё равно нужен ad-hoc или Enterprise-сертификат | Очень простая: загрузил `.ipa` → получил ссылку. Для тестировщика — просто открыть ссылку на устройстве |
| **Простота установки для тестировщика** | Высокая: установить приложение TestFlight → принять приглашение → скачать сборку | Средняя: получить email → перейти по ссылке → добавить профиль/установить (ad-hoc устройства должны быть зарегистрированы в provisioning profile) | Средняя: установка через Safari → «Install profile» → «Install app». Требует ручного подтверждения профиля в настройках |
| **Ограничения** | До 10 000 внешних тестировщиков, до 100 внутренних; отзывы Apple; сборка живёт 90 дней | До 200 тестеров в бесплатном плане; каждое устройство надо занести в provisioning profile (лимит 100 UDID для ad-hoc) | Бесплатный тариф: ссылки живут 5-10 часов после 3-х установок, до 10 «flashes»; всё равно нужен UDID устройства в provisioning profile |
| **Публичное распространение** | Да (публичная TestFlight-ссылка) | Нет, только по email/группам | Да, ссылка |
| **Аналитика/крэши** | Встроенная: Crash, feedback, screenshots | Интеграция с Crashlytics, аналитика внутри Firebase | Только базовая: количество установок |
| **Скорость доставки** | 24-48 ч (первая), затем часы | Минуты | Секунды |

### Рекомендация для нашего стартапа

**Рекомендую — TestFlight** как основной канал доставки, с Firebase App Distribution как «быстрый канал» для внутренних смоук-тестов.

**Аргументы:**

1. **Финансовое приложение — стандарт качества и безопасности.** TestFlight пропускает сборки через модерацию Apple, что помогает поймать вопиющие ошибки уже на этапе доставки. Для банковского приложения это плюс.
2. **Единый Apple Developer Program на $99/год закрывает и релиз в App Store, и TestFlight.** Стартап всё равно должен купить membership для будущего релиза — это не отдельная статья расхода.
3. **Простая установка для внешних тестировщиков** (нужен только TestFlight app и приглашение по email) — важно для «дружеских beta-тестов» и Focus group, что типично для финтех-стартапа.
4. **Отсутствие UDID-регистраций** (в отличие от Diawi/Firebase ad-hoc) экономит время QA-инженеров и позволяет масштабировать бета-программу без ограничения по устройствам.
5. **Firebase App Distribution — вспомогательный канал** для внутренней команды: там сборка доступна через 5-10 минут после билд-агента, что удобно для быстрых итераций и smoke-тестов внутри команды из 5-10 человек.

Diawi отклоняем: короткое время жизни ссылок, ручная возня с provisioning-профилями, никакой аналитики — плохо подходит для регулярной работы.

## 2. Чек-лист внешних прерывателей (interruption testing)

Обязательный чек-лист для проверки поведения приложения при внешних прерываниях. Все пункты выполняются на всех критичных экранах (авторизация, ввод карты, подтверждение платежа, вывод средств).

1. **Входящий телефонный звонок** (при активной сессии, при вводе PIN).
2. **Входящий видеозвонок** (WhatsApp / Telegram / FaceTime).
3. **SMS / MMS** с pop-up-уведомлением.
4. **Push-уведомление от другого приложения** (WhatsApp, календарь и т.п.).
5. **Push-уведомление от нашего же приложения** (например, «на карту поступил перевод»).
6. **Alarm-будильник / таймер** — часто вызывает полноэкранное прерывание.
7. **Разрыв сети** (Wi-Fi ↔ LTE ↔ полная потеря сигнала), в том числе в момент API-запроса.
8. **Переход между Wi-Fi-сетями** (например, при выходе из офиса).
9. **Разрядка батареи** до критичного уровня (<15%) и переход в режим энергосбережения.
10. **Обрыв питания** / резкое выключение устройства при активной операции.
11. **Свёртывание в фон (Home button / жест)** и возврат через N минут (30 сек, 5 мин, 30 мин, 24 часа).
12. **Переключение между приложениями** (мультизадачность, Split View на iPad).
13. **Блокировка экрана** (авто или кнопкой) во время платежа.
14. **Face ID / Touch ID prompt** от другого приложения (открывается поверх нашего).
15. **Плохая сеть с высоким packet loss** (симуляция через Network Link Conditioner / Charles Throttle).
16. **Переключение локали и языка системы** во время работы.
17. **Смена системного времени** (например, автоматический переход на летнее время).
18. **Всплывающие системные диалоги:** запрос обновления iOS, «недостаточно места», разрешение на камеру/геолокацию.
19. **AirDrop-принятие файла** во время сессии.
20. **Прерывание Bluetooth-подключения** (при NFC-оплате или разговоре через AirPods).

### Три наиболее критичных для финансового приложения + сценарии тестирования

#### Прерывание #1. Разрыв сети во время подтверждения платежа

**Почему критично:** пользователь видит «подтверждение отправлено», но сервер мог не получить/не завершить транзакцию. Возможны сценарии двойного списания, пропавших переводов, «висящих» операций.

**Сценарий (шаги):**
1. Войти в приложение, выбрать перевод по номеру телефона на 500 ₽ доверенному контакту.
2. Ввести сумму, подтвердить.
3. На экране «Введите SMS-код» ввести код, нажать «Подтвердить».
4. В момент между нажатием и получением ответа сервера **отключить интернет** (авиарежим или Charles → Throttle → 0 kbps).
5. Дождаться таймаута приложения (обычно 20-30 сек).
6. Включить интернет обратно.

**Ожидаемое:**
- Приложение показывает понятное сообщение об ошибке сети, а не «Что-то пошло не так».
- Есть возможность повторить операцию.
- После включения сети приложение самостоятельно проверяет статус транзакции по её `idempotency_key` и **не создаёт дубликат**.
- В истории операций либо появляется одна операция со статусом «В обработке» / «Успешно», либо ничего не появляется, если сервер не получил запрос.

#### Прерывание #2. Входящий звонок во время ввода PIN / биометрии

**Почему критично:** при звонке экран блокируется системным окном. Если PIN вводился и приложение «забывает» состояние, пользователь после сброса заново вводит PIN и может заблокировать себя (3-5 попыток → блок карты).

**Сценарий:**
1. Открыть приложение, увидеть экран ввода PIN-кода.
2. Ввести 2 первые цифры PIN.
3. Позвонить с другого телефона.
4. Ответить на звонок / отклонить / игнорировать (3 разных прогона).
5. Вернуться в приложение.

**Ожидаемое:**
- Все три сценария не приводят к автоматическому «списанию» попытки ввода PIN.
- Приложение либо полностью сбрасывает поле ввода (безопасно), либо продолжает с того же состояния — консистентно и понятно.
- Никаких «повисаний» на белом экране или крашей.
- Логи авторизации не содержат неудачных попыток из-за прерывания.

#### Прерывание #3. Полная потеря батареи во время транзакции

**Почему критично:** идентично сценарию с сетью — но восстановление сложнее, потому что пользователь может не сразу вернуться в приложение.

**Сценарий:**
1. Разрядить устройство до 5-10%.
2. Запустить транзакцию на 1000 ₽.
3. В момент показа экрана «Введите SMS-код» выключить устройство (кнопка / полное разряжение).
4. Зарядить устройство, включить, открыть приложение через 15 минут.

**Ожидаемое:**
- В истории операций видна операция в статусе «Отменена» либо не создана вовсе, но никогда не «Успешна» без факта подтверждения.
- Push от банка приходит с корректным статусом.
- Пользователь может повторить операцию без последствий.

## 3. Сообщение коллеге про утечки памяти в разных режимах приложения

> **Кому:** @dev-android-lead
> **От:** QA
> **Тема:** Как утечка памяти в нашем финансовом приложении проявляется в разных режимах — что тестируем
>
> Привет! Чтобы синхронизироваться перед регрессом, оставляю памятку — как утечка памяти может себя проявить в наших основных режимах работы, чтобы мы вместе понимали, что ищем.
>
> **1. Foreground / активная сессия (пользователь работает с приложением).**
> Утечка проявляется как **постепенное замедление интерфейса** и рост занятой RAM, видимой в Android Studio Profiler / Xcode Instruments. Пользователь чувствует «залипания» при скроллинге, растянутые анимации, растущий отклик кнопок. Наиболее уязвимые сцены: список транзакций (RecyclerView с изображениями чеков), карта отделений (кэш геоданных), экран графиков расходов.
>
> **2. Долгие сессии (пользователь работает 30+ минут без выхода).**
> Именно тут утечки видны отчётливее всего. Приложение начинает падать (OOM — OutOfMemoryError). На Android можно увидеть в Logcat: `A/libc: Fatal signal 6 (SIGABRT)` или `E/AndroidRuntime: java.lang.OutOfMemoryError`. На iOS в Instruments увидим стабильный рост «Persistent Bytes» — память, которая не освобождается между рабочими циклами.
>
> **3. Background (свёрнутое приложение).**
> Утечки в background особенно опасны — они «съедают» память, которая нужна ОС. Симптомы:
> - Приложение чаще, чем нужно, «убивается» системой (пропадает из recent apps), потому что превышает background-квоты.
> - Пользователь при возврате видит «холодный старт» вместо «горячего» — сессия сброшена, PIN нужно вводить заново.
> - На iOS: приложение чаще получает `applicationDidReceiveMemoryWarning`.
>
> **4. Смена сцен (навигация между экранами).**
> Классический тест на утечку: 20-30 раз пройти цикл «Главная → Переводы → Ввод суммы → Назад → Главная». Если после каждой итерации в profiler'е ступенькой растёт heap — есть leak, скорее всего на статических ссылках, singleton'ах или незакрытых listener'ах.
>
> **5. Прерывания (звонок, push).**
> Утечка ярко видна при возврате: приложение долго возвращается на экран, UI замирает на 1-3 секунды, статистика памяти показывает «пиковый» рост. Часто это причина: контекст Activity, удержанный в лямбдах или колбеках сетевых запросов, которые не были отменены при onPause.
>
> **6. Работа с картой / изображениями (сканирование промокодов, чеки).**
> Битмапы легко утекают: 4К-фото занимает ~40 МБ RAM. Если не освобождать — приложение падает за 5-10 сканирований. Тест: 30 раз открыть сканер, каждый раз сфотографировать чек, смотреть Memory Profiler.
>
> **7. Push-уведомления пришли пачкой в background.**
> Каждый push будит приложение и создаёт короткоживущие объекты. Если WorkManager / BroadcastReceiver держит ссылку на Application context «навсегда» — накапливается память в background без единого действия пользователя.
>
> План: пройдём этот список на новой сборке до релиза 2.4.0. Скину прикреплёнными скринами Profiler по каждой сцене.
>
> QA

## 4. Ответ: что такое утечка памяти в контексте мобильного приложения

**Утечка памяти (memory leak)** — это ситуация, когда мобильное приложение выделяет объекты в оперативной памяти, но по завершению их использования не освобождает эту память из-за сохранившихся ссылок. В результате garbage collector (на Android) или ARC (на iOS) не могут удалить объекты, и потребление RAM растёт со временем, даже если пользователь совершает те же действия по кругу.

Проще говоря — это память, которая занята, но никому не нужна: приложение уже не пользуется этими объектами, но и «отпустить» их не может.

**Практические последствия для пользователя:**
- Приложение постепенно замедляется, интерфейс подлагивает.
- ОС «убивает» приложение при нехватке памяти (OOM Killer), пользователь теряет сессию.
- Ускоренный расход батареи и нагрев устройства.
- В худшем случае — краш всего приложения с потерей несохранённых данных.

**Типичные причины утечек:**
- **На Android:** удерживание Context/Activity в статических полях, singleton'ах, лямбдах, незакрытые Handler / AsyncTask / BroadcastReceiver, non-static inner classes.
- **На iOS:** сильные ссылки (`strong`) в замыканиях без `[weak self]`, retain cycles между двумя объектами, не отписанные NotificationCenter observers.
- **Общее:** битмапы и медиа, не сброшенные вручную; кэш без ограничения по размеру; открытые файловые/сетевые ресурсы.

**Как тестировщик её ловит:**
- Android Studio Memory Profiler / LeakCanary — показывает heap и trace утечки.
- Xcode Instruments (Allocations, Leaks) — детектирует retain cycle'ы.
- Долгие smoke-сессии с повторяющимся сценарием — если heap растёт «ступенькой», есть утечка.
