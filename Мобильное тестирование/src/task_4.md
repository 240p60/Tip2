# Задание 4. Логи и логирование

**Проблема:** мобильное приложение онлайн-банка аварийно завершает работу (краш) при попытке просмотреть историю операций за последний месяц.

---

## 1. Наиболее важные уровни логов для анализа

В Android Logcat / iOS Console выделяют 6 уровней (в порядке возрастания важности):

| Уровень | Symbol | Что содержит | Полезно для нашего случая? |
|---------|:------:|--------------|:---------------------------:|
| Verbose | V | Подробные технические записи, включая шаги отладки | ⚠ Частично |
| Debug | D | Отладочные сообщения от разработчика | ⚠ Частично |
| Info | I | События нормальной работы (пользователь открыл экран, отправил запрос) | ✅ Да |
| Warn | W | Предупреждения — что-то пошло не по плану, но выжило | ✅ Да |
| Error | E | Ошибки — операция не выполнена | ✅✅ **Ключевой** |
| Assert / Fatal | A/F | Критические сбои, приложение падает | ✅✅ **Ключевой** |

### Обоснование выбора уровней

**Ключевые уровни для нашего краша:**

1. **Fatal / Assert (A / F)** — самый первый уровень, куда я смотрю. Именно здесь будет запись о самом падении: `FATAL EXCEPTION: main`, тип исключения, стек-трейс.
2. **Error (E)** — второй по приоритету. Часто краш — это следствие цепочки ошибок: сначала failed запрос, потом плохой парсинг, потом NPE. Ошибки уровня E раскрывают эту цепочку.
3. **Warn (W)** — предупреждения помогают восстановить контекст: «получен ответ от сервера с неожиданной структурой», «на списке нет ожидаемого поля» — часто прямо предшествуют падению.
4. **Info (I)** — важен для реконструкции пользовательского пути: увидим шаги «пользователь открыл экран Операций → отправлен GET /transactions → получено 200 OK, 340 записей» и т.д. Без этого сложно понять, на каком именно шаге упало.

**Уровни Verbose (V) и Debug (D)** держим включёнными, но фильтруем — их слишком много, чтобы читать глазами; они пригодятся только если нужно углубиться в конкретный участок кода.

### Практический подход

Начинаю с `level:error` + `level:assert` — сужаю поток до нескольких десятков строк.
Затем расширяю до `level:warn` — картина становится полнее.
Затем добавляю `level:info` только для нужного тега / процесса — чтобы восстановить контекст, но не утонуть в потоке.

## 2. Механизм получения логов

Основной инструмент — **Logcat** (для Android). Он читает системный кольцевой буфер логов ядра Android + логи приложений.

### Базовые шаги для получения логов

**Способ А — через Android Studio (когда есть IDE)**

1. Подключить устройство по USB (с включённым **USB debugging** из режима разработчика — см. `task_3.md`) или запустить эмулятор.
2. Открыть Android Studio → нижняя панель **Logcat** (`Alt+6` / `⌘6`).
3. В верхнем выпадающем списке выбрать устройство и, при необходимости, конкретный процесс (`com.example.bank`).
4. Установить фильтр по уровню (см. §3).
5. Начать воспроизведение краша — Logcat автоматически покажет поток логов.
6. После падения — правый клик по интересным строкам → **Save selected items…** → сохранить как `.txt` для приложения к баг-репорту.

**Способ Б — через `adb` в командной строке (когда IDE недоступна)**

Это классический путь для QA-инженера, который часто работает без Android Studio.

```bash
# 1. Убедиться, что устройство видно
adb devices
# List of devices attached
# emulator-5554  device

# 2. Очистить буфер, чтобы получить чистый лог падения
adb logcat -c

# 3. Начать сохранение логов в файл
adb logcat -v threadtime > bank_crash_2026-05-10.log

# 4. Воспроизвести баг (открыть экран Операций → выбрать «Последний месяц»)

# 5. После падения — прервать запись Ctrl+C

# 6. Открыть файл в любом текстовом редакторе, искать FATAL / Exception / Error
```

Ключевые флаги `adb logcat`:
- `-v threadtime` — формат «дата время PID TID уровень тег: сообщение» (стандарт де-факто);
- `-b main,system,crash` — читать несколько буферов сразу (в crash-buffer лежат самые интересные для нас записи);
- `-t 1000` — «последние 1000 строк» (полезно, если не хочешь копить огромный файл);
- `--pid=$(adb shell pidof com.example.bank)` — фильтрация только по нашему приложению.

**Способ В — bug report от разработчиков**

Если баг воспроизводится только на конкретном устройстве пользователя, разработчик может попросить прислать полный `bugreport` через `adb bugreport`. Это zip-архив с системными логами, снимками процессов и т.п. — для расследования сложных крашей.

## 3. Фильтры Logcat для быстрого поиска причины

Ниже — конкретные фильтры для нашего кейса «краш при открытии истории операций».

### Пример 1. Фильтр только по нашему приложению + Error и выше

```
package:mine level:error
```
или в терминале:
```bash
adb logcat --pid=$(adb shell pidof com.example.bank) *:E
```

**Что даст:** резко сузит поток до собственных ошибок приложения. Здесь скорее всего найдётся `FATAL EXCEPTION` и стек-трейс.

### Пример 2. По тегу `AndroidRuntime` — где живут crash'ы Java/Kotlin

```
tag:AndroidRuntime
```
или в терминале:
```bash
adb logcat AndroidRuntime:E *:S
```

**Что даст:** отфильтрует только сообщения о падениях runtime-исключений. Первая строка обычно — `FATAL EXCEPTION: main`, дальше — тип исключения и стек.

### Пример 3. По ключевым словам, характерным для нашего сценария

```
message:transaction | message:history | message:operations
```
или регуляркой:
```
transactions|Statement|history
```

**Что даст:** покажет все логи, где упомянуто «transactions» или «history» — быстрое понимание, какой сетевой запрос отправился и что именно вернулось.

### Пример 4. Логи сетевого клиента (обычно OkHttp/Retrofit)

```
tag:OkHttp
```
или
```
tag:Retrofit
```

**Что даст:** покажет полные HTTP-запросы и ответы — с полями. Если краш случился при парсинге ответа, здесь мы увидим точное тело JSON, вызвавшее проблему.

### Пример 5. Комбинированный «под наш кейс»

```
package:com.example.bank level:warn (tag:AndroidRuntime | tag:OkHttp | message:transaction)
```

**Что даст:** ровно один короткий читаемый поток: наши предупреждения и ошибки + сетевые вызовы + шаги пути пользователя.

### Пример 6. Быстрый поиск NullPointerException и OutOfMemory

```
message:NullPointerException | message:OutOfMemoryError
```

**Что даст:** две самые частые причины крашей на Android — сразу видно, случалась ли хоть одна.

### Что видно из логов (для разработчика в разделе «Гипотеза»)

1. Пользователь выбрал фильтр «Последний месяц» — запрос ушёл на бэкенд.
2. Сервер вернул **200 OK** и объёмный ответ (~85 КБ, около 100+ операций).
3. `OperationsMapper` уже дважды получил `null` в неожиданных полях (`category`, `merchant.name`) — приложение справилось с помощью fallback.
4. На **третьем случае** — `Merchant` пришёл целиком `null`, и `OperationsAdapter.onBindViewHolder` попытался вызвать `merchant.getIconUrl()` → `NullPointerException` → краш.
5. **Место падения:** `OperationsAdapter.kt:87`.

**Предположения по фиксу:**
- Добавить null-safe доступ: `merchant?.iconUrl ?: R.drawable.merchant_placeholder`.
- Валидировать контракт с бэкендом: возможно ли `merchant == null`, или бэкенд «сломался» на конкретных операциях (например, переводы между своими счетами не имеют мерчанта).
- Добавить тест-кейс: получить `null` в `merchant` — приложение должно показать иконку по умолчанию, а не падать.

**Куда эскалировать:** Frontend Android team (владелец экрана Operations) + запрос к Backend team на подтверждение контракта поля `merchant` в `/v2/operations`.
