# Задание 1. Виды безопасности

## Введение

Анализируемое приложение — **«Безопасный чат для врачей и пациентов»**. Это веб-приложение, в котором врач и пациент обмениваются сообщениями, содержащими особо чувствительные данные: диагнозы, назначения, результаты анализов, персональные данные (ФИО, дата рождения, полис, контакты).

**Предполагаемая функциональность (на её основе строим анализ угроз):**
- регистрация и авторизация врача и пациента (логин/пароль + 2FA);
- личный кабинет с историей переписок;
- текстовый чат в реальном времени (WebSocket);
- отправка файлов и изображений (снимки, PDF-выписки, фото рецептов);
- push/email-уведомления о новых сообщениях;
- поиск по истории сообщений;
- хранение переписки на сервере.

**Правовой контекст (РФ):** данные относятся к специальной категории ПДн и врачебной тайне. Обработка регулируется 152-ФЗ «О персональных данных», 323-ФЗ «Об охране здоровья» (врачебная тайна), приказами ФСТЭК/ФСБ по защите ИСПДн. Утечка = крупные оборотные штрафы + репутационный крах + уголовная ответственность за разглашение врачебной тайны.

Ниже — предварительный анализ угроз по трём принципам защищённого приложения: **конфиденциальность, целостность, доступность**.

## 1. Риски нарушения КОНФИДЕНЦИАЛЬНОСТИ

*(данные чата могут стать доступны посторонним)*

| # | Риск / сценарий | Причина проблемы безопасности |
|---|-----------------|-------------------------------|
| К1 | **Отсутствие сквозного (E2E) шифрования** — переписка хранится и передаётся в открытом виде, администратор БД или взломщик сервера видит все диагнозы. | Несоответствие функциональным требованиям ИБ (не заложено шифрование данных при хранении и передаче) |
| К2 | **IDOR (Insecure Direct Object Reference)** — сменив `chat_id` в URL/API (`/api/chats/1024` → `/api/chats/1025`), пользователь получает чужую переписку. | Ошибки в серверном коде (нет проверки прав доступа к объекту, авторизация не привязана к владельцу) |
| К3 | **XSS в поле сообщения** — злоумышленник отправляет `<script>`, крадущий cookie/сессию собеседника и historию чата. | Ошибки в клиентском/серверном коде (нет экранирования пользовательского ввода) |
| К4 | **Передача по HTTP или со слабым TLS** — трафик перехватывается в публичном Wi-Fi (MITM), диагнозы читаются «на лету». | Некорректная конфигурация инфраструктуры (нет принудительного HTTPS/HSTS, устаревший TLS) |
| К5 | **Утечка данных через сторонний код/аналитику** — подключённый сторонний скрипт (чат-виджет, метрика) отправляет тексты сообщений на внешний сервер. | Ошибки в подключаемом коде (доверие сторонним библиотекам без аудита, нет CSP) |

## 2. Риски нарушения ЦЕЛОСТНОСТИ

*(сообщения или файлы могут быть изменены без ведома участников)*

| # | Риск / сценарий | Причина проблемы безопасности |
|---|-----------------|-------------------------------|
| Ц1 | **Подмена сообщения при передаче (MITM)** — атакующий меняет дозировку в назначении («принимать 1 таблетку» → «10 таблеток»). | Некорректная конфигурация инфраструктуры (нет TLS/контроля целостности канала) |
| Ц2 | **Модификация данных в БД без аудита** — инсайдер/взломщик правит текст сообщения напрямую в базе, следов не остаётся. | Несоответствие функциональным требованиям ИБ (нет журналирования, контрольных сумм, неизменяемого лога) |
| Ц3 | **Подмена вложения (файла)** — вместо загруженной выписки подставляется другой PDF из-за отсутствия проверки хеша/подписи файла. | Ошибки в серверном коде (нет проверки целостности и типа файла при хранении/выдаче) |
| Ц4 | **CSRF** — врач авторизован; злоумышленник вынуждает его браузер отправить поддельный запрос, меняющий/удаляющий сообщение. | Ошибки в серверном коде (нет CSRF-токенов, проверки Origin/Referer) |
| Ц5 | **Отсутствие защиты от повторной отправки (replay)** — перехваченный запрос отправки назначения дублируется, пациент получает два противоречивых назначения. | Несоответствие функциональным требованиям ИБ (нет nonce/idempotency-ключей) |

## 3. Риски нарушения ДОСТУПНОСТИ

*(легитимный пользователь не сможет получить доступ в критический момент)*

| # | Риск / сценарий | Причина проблемы безопасности |
|---|-----------------|-------------------------------|
| Д1 | **DDoS-атака на чат** — сервис недоступен, врач не может передать экстренное назначение пациенту в критический момент. | Некорректная конфигурация инфраструктуры (нет anti-DDoS, rate-limit, автоскейлинга) |
| Д2 | **Блокировка аккаунта перебором (account lockout как оружие)** — злоумышленник намеренно вводит неверные пароли на аккаунт врача, система блокирует его, врач не может войти. | Несоответствие функциональным требованиям ИБ (защита от брутфорса реализована без учёта DoS-побочки, нет captcha/ступенчатых задержек) |
| Д3 | **Отсутствие резервирования / единая точка отказа** — падение единственного сервера БД делает всю историю переписок недоступной. | Некорректная конфигурация инфраструктуры (нет отказоустойчивости, горячего резерва) |
| Д4 | **Ransomware / повреждение данных без бэкапа** — шифровальщик или сбой диска уничтожает переписки, восстановить нечем. | Некорректная конфигурация инфраструктуры (нет регулярных проверенных бэкапов) |
| Д5 | **Логическая ошибка в сессиях** — истечение токена в момент активного диалога выкидывает пользователя, а повторный вход не работает из-за бага. | Ошибки в серверном коде (некорректное управление жизненным циклом сессии) |

### 4.2. Топ-3 критических риска (выбор группы)

**🥇 Риск №1 — К1: Отсутствие сквозного шифрования (конфиденциальность).**
Обоснование: для медицинского чата это самая тяжёлая угроза. Диагнозы и врачебная тайна в открытом виде = нарушение 152-ФЗ и 323-ФЗ. Одна утечка БД раскрывает все переписки всех пациентов сразу. Максимальный ущерб (юридический, репутационный, для здоровья пациентов) при высокой вероятности, если шифрование не заложено изначально.

**🥈 Риск №2 — К2: IDOR — доступ к чужой переписке (конфиденциальность).**
Обоснование: тривиально эксплуатируется (перебор ID в API), не требует навыков, массово раскрывает чужие медицинские данные. Классика OWASP (Broken Access Control — #1 в OWASP Top-10 2021). Один незакрытый эндпоинт = утечка данных тысяч пациентов.

**🥉 Риск №3 — Ц1: Подмена сообщения при передаче (целостность).**
Обоснование: уникально опасен именно для медицины — подмена дозировки или назначения может напрямую нанести вред здоровью или жизни пациента. Это не «просто утечка», а физический риск. Поэтому группа ставит его выше остальных рисков доступности/целостности.

### 4.3. Рекомендации для разработчиков (митигации топ-3)

**Для К1 (нет E2E-шифрования):**
1. Внедрить **сквозное шифрование (E2EE)** сообщений (например, на базе протокола Signal / libsodium): расшифровать переписку могут только клиенты врача и пациента, но не сервер.
2. Шифровать данные **at rest** (шифрование БД и файлового хранилища, например AES-256-GCM) и **in transit** (TLS 1.3 с HSTS). Ключи хранить в KMS/HSM, а не в коде.

**Для К2 (IDOR):**
1. Реализовать **серверную проверку авторизации на уровне объекта**: перед выдачей чата проверять, что `current_user.id` является участником запрашиваемого `chat_id`, а не полагаться на «скрытость» ID.
2. Использовать **непредсказуемые идентификаторы** (UUID вместо последовательных int) как defense-in-depth + добавить автотесты на broken access control (попытка обратиться к чужому ресурсу должна возвращать 403/404).

**Для Ц1 (подмена сообщения при передаче):**
1. Обеспечить **целостность канала**: TLS 1.3 + при E2EE использовать аутентифицированное шифрование (AEAD), где любая модификация шифротекста делает его невалидным при расшифровке.
2. Добавить **подпись/HMAC сообщений и вложений** и проверку на клиенте: если подпись не сходится — сообщение помечается как «повреждено/скомпрометировано» и не показывается как достоверное.
