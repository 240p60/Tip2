# Задание 2. Инструменты криптографии

## 1. Разница между кодированием, хешированием и шифрованием

| Свойство | **Кодирование** | **Хеширование** | **Шифрование** |
|----------|-----------------|-----------------|----------------|
| Цель | Преобразование данных в другой формат для совместимости/передачи | Получение фиксированного «отпечатка» данных | Защита данных от прочтения посторонними |
| Обратимость | Обратимо **без ключа** (любой может декодировать) | **Необратимо** (нельзя восстановить исходные данные) | Обратимо **только с ключом** |
| Нужен ли ключ | Нет | Нет (но бывает соль/HMAC-ключ) | Да (симметричный или пара ключей) |
| Обеспечивает секретность? | ❌ Нет | ❌ Нет (но скрывает исходное значение) | ✅ Да |
| Примеры | Base64, URL-encoding, ASCII, UTF-8 | SHA-256, bcrypt, Argon2 | AES, RSA, ChaCha20 |

### Ключевое различие

- **Кодирование ≠ защита.** Base64 — это НЕ безопасность. Многие новички считают, что «закодировал в Base64 = защитил». Это ошибка: декодировать может кто угодно за секунду. Кодирование нужно только для формата (например, передать бинарные данные в текстовом JSON).
- **Хеширование** — «одностороння дверь»: из данных легко получить хеш, но из хеша нельзя восстановить данные. Используется для проверки целостности и хранения паролей.
- **Шифрование** — «сейф с ключом»: данные можно и зашифровать, и расшифровать, но только тому, у кого есть ключ.

### Реальные примеры использования в веб-приложении

1. **Кодирование (Base64):** передача файла-вложения (картинки) внутри JSON API-ответа как `data:image/png;base64,iVBOR...`, либо кодирование JWT-заголовка и payload (именно **кодирование**, не шифрование — содержимое JWT читается любым, кто раскодирует Base64!).

2. **Хеширование (bcrypt/Argon2):** хранение паролей пользователей. В БД лежит не пароль, а его хеш с солью. При входе система хеширует введённый пароль и сравнивает хеши — сам пароль сервер не хранит и «не знает».

3. **Шифрование (AES-256 / TLS):** защита трафика между браузером и сервером (HTTPS/TLS), а также шифрование чувствительных данных в БД (например, номеров карт, паспортных данных) алгоритмом AES-256-GCM.

## 2. Симметричное vs асимметричное шифрование (объяснение для менеджера)

### Аналогия «для бизнеса»

> **Симметричное шифрование — это как обычный дверной замок с одним ключом.**
> Один и тот же ключ и запирает, и отпирает дверь. Если я хочу, чтобы ты открыл мою дверь, я должен передать тебе копию ключа. Проблема: **как безопасно передать ключ?** Если его перехватят по дороге — замок бесполезен.
>
> **Асимметричное шифрование — это как почтовый ящик с прорезью.**
> У ящика есть два разных «ключа»:
> - **Публичный** (открытая прорезь) — любой может бросить письмо внутрь (зашифровать). Прорезь можно показывать всем.
> - **Приватный** (ключ от дверцы ящика) — только владелец может открыть ящик и достать письма (расшифровать). Этот ключ никому не передаётся.
>
> Красота в том, что для отправки секрета мне **не нужно заранее обмениваться секретным ключом** — я беру публичный ключ получателя (он открыт всем), шифрую, и расшифровать сможет только владелец приватного ключа.

### Краткая сводка

| | **Симметричное** | **Асимметричное** |
|---|-----------------|-------------------|
| **Определение** | Один общий ключ для шифрования и расшифрования | Пара ключей: публичный (шифрует) + приватный (расшифровывает) |
| **Аналогия** | Замок с одним ключом (нужны копии у всех) | Почтовый ящик: прорезь для всех, ключ от дверцы — у одного |
| **Плюсы** | Очень быстрое, подходит для больших объёмов данных | Не нужно заранее передавать секретный ключ; решает проблему обмена ключами; позволяет цифровую подпись |
| **Минусы** | Проблема безопасной передачи ключа; при утечке ключа скомпрометировано всё | Медленное, не подходит для больших объёмов данных |
| **Примеры** | AES, ChaCha20, 3DES (устар.) | RSA, ECC (эллиптические кривые), Diffie-Hellman |
| **Где применяется** | Шифрование данных «в покое», содержимого сессии | Обмен ключами, TLS-handshake, цифровые подписи, сертификаты |

### Как они работают вместе (важно для менеджера)

В реальности (например, в HTTPS) используются **оба сразу**: асимметричное — чтобы безопасно договориться об общем секретном ключе в начале соединения (решает проблему передачи ключа), а дальше — быстрое симметричное для шифрования самого трафика. Это называется гибридное шифрование: «безопасность асимметрии + скорость симметрии».

## 3. «Чёрный» и «белый» списки алгоритмов

### 🚫 Чёрный список (устаревшие / небезопасные)

#### Шифрование

| Алгоритм | Почему в чёрном списке | Уязвим к атакам |
|----------|------------------------|-----------------|
| **DES** (Data Encryption Standard) | Ключ всего 56 бит — слишком короткий для современных мощностей | **Brute-force (полный перебор)** — взламывается за часы/минуты на современном железе |
| **3DES (Triple DES)** | Формально усилен, но медленный, блок 64 бита | **Sweet32 (birthday attack на блочных шифрах)** — при большом объёме трафика восстанавливается открытый текст; официально запрещён NIST с 2023 |
| **RC4** (потоковый) | Статистические смещения в ключевом потоке | **Атаки на смещения ключевого потока (biased bytes)** — восстановление части открытого текста (использовалась в атаках на WEP/TLS) |

#### Хеширование

| Алгоритм | Почему в чёрном списке | Уязвим к атакам |
|----------|------------------------|-----------------|
| **MD5** | Найдены практические коллизии | **Коллизионные атаки** — можно подобрать два разных входа с одинаковым хешем (использовалось для поддельных сертификатов, вредоносного ПО Flame) |
| **SHA-1** | Теоретические, а затем и практические коллизии (Google SHAttered, 2017) | **Коллизионные атаки** — доказана возможность коллизий; запрещён для сертификатов и подписей |
| **Простой SHA-256 без соли для паролей** | Слишком быстрый для хранения паролей | **Rainbow tables / brute-force по словарю** — GPU перебирает миллиарды хешей в секунду; для паролей нужны медленные функции |

### ✅ Белый список (рекомендованные)

#### Шифрование

| Алгоритм | Почему безопасен |
|----------|------------------|
| **AES-256 (в режиме GCM)** | Стойкий блочный шифр, ключ 256 бит (перебор невозможен даже теоретически); режим GCM даёт аутентифицированное шифрование (AEAD) — обнаруживает любую модификацию шифротекста. Государственный стандарт США, широко проверен криптосообществом. |
| **ChaCha20-Poly1305** | Быстрый потоковый AEAD-шифр, отлично работает без аппаратного ускорения (мобильные устройства); нет известных практических атак; используется в TLS 1.3 и WireGuard. |

#### Хеширование

| Алгоритм | Почему безопасен |
|----------|------------------|
| **Argon2id** | Победитель Password Hashing Competition (2015). Специально «медленный» и требователен к памяти → делает перебор на GPU/ASIC невыгодным; настраиваемые параметры стоимости; рекомендован OWASP №1 для паролей. |
| **bcrypt** | Проверенная временем функция хеширования паролей с настраиваемым «cost factor» (адаптируется под рост мощностей) и встроенной солью; стойка к rainbow tables и GPU-brute-force. Хорошая альтернатива, если Argon2 недоступен. |
| **SHA-256 / SHA-3** *(для целостности, не паролей)* | Для проверки целостности файлов и цифровых подписей (не для паролей!) — коллизий не найдено, криптостойкие. |

**Ключевое правило для QA:** пароли → медленный алгоритм (Argon2id/bcrypt); целостность файлов → SHA-256/SHA-3; шифрование данных → AES-256-GCM или ChaCha20-Poly1305. Увидел MD5/SHA-1 для паролей или DES/RC4 — это баг безопасности.

## 4. Тест-план базовой безопасности интернет-магазина электроники

**Фокус:** ручное тестирование. Выбраны 3 области: **Вход в аккаунт**, **Личный кабинет пользователя**, **Оформление заказа**.

### Область 1. Вход в аккаунт (логин/пароль)

| Что проверяем | Как проверяем | На что обращать внимание |
|---------------|---------------|--------------------------|
| Защита от брутфорса | Ввести 10+ раз неверный пароль | После N попыток — captcha / временная блокировка / задержка. Не должно быть безлимитных попыток |
| Передача учётных данных | Открыть DevTools → Network при логине | Логин/пароль уходят **только по HTTPS** методом POST (не GET, не в URL). Пароль не логируется в открытом виде |
| Хранение пароля | (по возможности с dev-командой) посмотреть БД | Пароль хранится как хеш (bcrypt/Argon2), не в открытом виде и не в MD5 |
| Перечисление пользователей (user enumeration) | Ввести существующий и несуществующий email | Сообщение об ошибке **одинаковое** («неверный логин или пароль»), не «такого пользователя нет» — иначе можно собирать базу email |
| Восстановление пароля | Запросить сброс пароля | Ссылка одноразовая, с коротким TTL, не предсказуемая; старый пароль не приходит в письме открытым текстом |
| SQL-инъекция в форме входа | Ввести `' OR '1'='1` в логин/пароль | Не должно быть входа/ошибки БД. Должна быть стандартная ошибка авторизации |
| Флаги сессионной cookie | DevTools → Application → Cookies | У session-cookie флаги `Secure`, `HttpOnly`, `SameSite` |

### Область 2. Личный кабинет пользователя

| Что проверяем | Как проверяем | На что обращать внимание |
|---------------|---------------|--------------------------|
| IDOR (доступ к чужим данным) | В URL/API поменять `user_id=1001` на `1002` | Нельзя получить чужой профиль/заказы. Должно быть 403/404 |
| XSS в полях профиля | В имя/адрес ввести `<script>alert(1)</script>` | Скрипт не выполняется, данные экранируются при отображении |
| Хранение персональных данных | DevTools → Network при открытии кабинета | ПДн передаются по HTTPS; карты/паспорт замаскированы (`**** 1234`) |
| Изменение email/пароля | Сменить пароль | Требуется подтверждение текущего пароля; приходит уведомление на старый email |
| Доступ после разлогина | Разлогиниться → нажать «Назад» в браузере | Кабинет не отображается из кэша, требуется повторный вход |
| CSRF на изменение данных | Проверить наличие CSRF-токена в формах | Формы изменения данных защищены токеном/проверкой Origin |

### Область 3. Оформление заказа

| Что проверяем | Как проверяем | На что обращать внимание |
|---------------|---------------|--------------------------|
| Подмена цены / суммы | В DevTools/прокси перехватить запрос оформления, изменить `price`/`total` | Сервер **пересчитывает** сумму сам, не доверяет цене от клиента. Заказ с подменённой ценой отклоняется |
| Манипуляция количеством | Ввести отрицательное/дробное количество (`-5`, `0`, `9999999`) | Валидация на сервере: нельзя заказать отрицательное кол-во (иначе «отрицательная сумма» = мошенничество) |
| IDOR на чужой заказ/адрес | Подставить чужой `order_id` / `address_id` | Нельзя оформить заказ на чужой адрес или увидеть чужой заказ |
| Данные платежа | DevTools → Network при оплате | Платёжные данные идут на PCI-DSS-совместимый шлюз по HTTPS, не хранятся на нашем сервере в открытом виде |
| Повторная отправка (replay) | Отправить один и тот же запрос оплаты дважды | Защита от двойного списания (idempotency-ключ) |
| Промокоды | Применить один промокод многократно / истёкший | Сервер валидирует лимиты и срок действия промокода |

### Веб-инструменты тестировщика

| Инструмент | Для чего |
|-----------|----------|
| **Chrome DevTools** (Network, Application, Console) | Просмотр запросов/ответов, cookie и их флагов, локального хранилища, ошибок JS |
| **Burp Suite (Community)** / **OWASP ZAP** | Перехват и модификация запросов, автоматическое сканирование уязвимостей, повтор запросов (Repeater) |
| **Postman / Insomnia** | Ручная отправка API-запросов с подменёнными параметрами, тест авторизации |
| **Charles Proxy / Fiddler** | Перехват трафика, подмена ответов, throttling (см. проект «Мобильное тестирование») |
| **Онлайн-сервисы** (SSL Labs, securityheaders.com) | Проверка качества TLS-конфигурации и HTTP-заголовков безопасности (CSP, HSTS, X-Frame-Options) |
| **jwt.io** | Декодирование и анализ JWT-токенов (проверить, что там нет чувствительных данных и слабой подписи) |

## Проверка ситуации: «Пользователь забыл разлогиниться на общественном компьютере»

### Как это можно проверить?

1. **Тест таймаута сессии (session timeout):**
   - Войти в аккаунт, оставить вкладку неактивной на N минут (5, 15, 30).
   - Вернуться и попробовать выполнить действие (открыть заказы, оформить покупку).
   - **Ожидание:** после разумного периода бездействия сессия истекает, требуется повторный вход.

2. **Тест «кнопки Назад» после логаута:**
   - Разлогиниться, нажать «Назад» в браузере.
   - **Ожидание:** страница личного кабинета не показывается из кэша, идёт редирект на логин.

3. **Тест живучести cookie после закрытия браузера:**
   - Войти, закрыть браузер полностью, открыть снова, зайти на сайт.
   - **Ожидание:** для «чужого/общественного» ПК сессия не должна автоматически продлеваться навечно — либо запрос повторной авторизации, либо ограниченный срок жизни session-cookie.

4. **Тест одновременных сессий и удалённого выхода:**
   - Войти с двух устройств, на одном нажать «Выйти со всех устройств».
   - **Ожидание:** сессия на общественном ПК немедленно завершается.

5. **Проверка данных в браузере после выхода:**
   - После логаута открыть DevTools → Application → Cookies / Local Storage / Session Storage.
   - **Ожидание:** сессионные токены и чувствительные данные **удалены**, не остаются в хранилище браузера.

### Что должно происходить для защиты?

- **Автоматический таймаут сессии** по бездействию (idle timeout, например 15-30 минут) + абсолютный лимит жизни сессии (например 8-12 часов).
- **Полная инвалидизация сессии на сервере при логауте** — токен становится недействительным на бэкенде, а не только «стирается» на клиенте.
- **Очистка cookie, Local/Session Storage** при выходе; сессионные cookie (без `Expires`/`Max-Age`) удаляются при закрытии браузера.
- **Флаги cookie:** `HttpOnly` (защита от кражи через XSS), `Secure` (только HTTPS), `SameSite=Lax/Strict` (защита от CSRF).
- **Функция «Выйти со всех устройств»** и список активных сессий в личном кабинете.
- **Отключённая опция «запомнить меня» по умолчанию** + предупреждение «не ставьте на чужом компьютере».
- **Отсутствие кэширования** приватных страниц: заголовки `Cache-Control: no-store, no-cache`, `Pragma: no-cache` — чтобы «Назад» не показывал данные.
- **Повторная аутентификация для критичных действий** (смена пароля, оформление дорогого заказа, привязка карты) даже в активной сессии.
